Back in February, when I wrote [Human in the End](/thoughts/human-in-the-end-next-gen-agent-interaction), my picture of [Alan](https://alanworks.app) was fairly simple: a Rust agent runtime built around the metaphor of a Turing machine, with a stateless program running over a stateful tape.

It has been a while, so I no longer remember the exact moment that picture broke down. What I do remember is a stretch where I was pushing many things on Alan in parallel: plugins, apps, different UI experiments. The more I built, the more something felt off in the underlying abstraction. Every new surface seemed to demand another layer of glue, and the pieces never quite settled together.

I have always liked Unix. Since I had already borrowed the Turing machine metaphor for Alan, a natural question followed: why not actually build something like Unix? What would Unix look like in the age of agents? How could an agent really be integrated with an operating system instead of sitting awkwardly on top of it as another application wrapper?

I started reading and researching around those questions, and **Plan 9** matched what I had in mind far more closely than anything else. That is where **`alan9`**, the system layer underneath Alan, came from.

## Agent as a Filesystem

Plan 9's central idea is familiar: **everything is a file**.

Applied to AI, it feels surprisingly direct. At the bottom, an LLM is a machine that generates characters. If its input and output are already streams of text, why not represent it as a file, or a stream behind a file?

Once you follow that thought, an entire agent can be treated as a filesystem. The model is a stream. The agent itself is an ordinary process. Its state, context, tools, and memory are files and directories mounted into its namespace, and what it can touch is simply whatever has been mounted there.

For me, this was not just about finding a neat systems metaphor. It tied directly into another belief I hold about AI software: **conversational UI is not necessarily the final form of the AI era.**

Chat works for many things, but for most users, well-designed UI and UX still matter a great deal. What I actually want is for different vertical apps to share the same agent foundation underneath. Some of the things I have been experimenting with lately, like M3 and [slowpage](https://github.com/realmorrisliu/slowpage) (a reader app), come out of this exact direction. Their UI and UX are still nowhere near the level I want, to be honest, but the underlying idea holds up.

Looking at the problem from those vertical apps, treating an agent as a filesystem turns out to be a very clean abstraction. The biggest practical advantage is that you do not need special-purpose plumbing to handle agent output. State, events, and streams are already shaped inside the filesystem, so an app just reads and writes files instead of coupling itself to a bespoke chat protocol or SDK. And because everything is text and files, standard text tools work out of the box.

You stop inventing a new API every time you want a different interface or a new capability. The foundation and the apps meet at the simplest boundary there is.

## Letting Go of Alan for macOS

For a while, I also put real effort into **Alan for macOS**, trying to build a good terminal manager. Technically, it had quite a bit in common with tools like Superlogical's Rex that have become popular recently.

While working on it, though, too many concerns started tangling together. Window management, terminal behavior, and the agent foundation itself blurred into each other, and it became harder to think clearly about where a given problem belonged.

When I stepped back and looked at my actual goal, the outer shell did not seem that important, at least not right now. Trying to maintain a terminal shell was pulling attention away from the agent itself. So I dropped it, focused back on the foundation, and left terminal management to dedicated hosts.

In hindsight, removing it made the whole project easier to think about.

## Explicit Boundaries, and Second Thoughts

One way `alan9` goes against the grain of most CLI agents today is how strict it is about boundaries. Most tools in this space automatically adopt your current directory, scan local dotfiles, and inherit environment variables the moment you run them. In `alan9`, I deliberately pushed the other way: directories have to be mounted explicitly, and installing a package does not automatically grant running processes access to it.

Three things drove that choice at the time. First was safety. There are plenty of stories online of agents doing something wrong with catastrophic consequences, and handing an agent ambient access by default never sat right with me. Second was borrowing from containerization, keeping isolation clean so Alan could eventually run in more environments, even edge environments. Third was context engineering: I thought showing an agent only what it genuinely needed to see was crucial.

To be honest, though, those were my observations at the time, and some of them may already be wrong or outdated. Tightening every boundary adds real friction in day-to-day use. Part of what I need to figure out next for Alan is the other side of the problem: how an agent can get the context and resources it needs more intelligently, without giving up safety altogether.

## Looking Ahead

Alan is still very early. Neither `alan9` nor the apps on top of it are finished, and some of the assumptions I hold today will probably change again as I keep using them.

I am not writing this to announce a finished system. I just find **agent as a filesystem** to be an unusually clean abstraction. Bringing AI back to old, restrained primitives like files, streams, and namespaces makes a lot of tangled problems feel simpler. If you are building agents or thinking about how software should sit on top of them, I hope the idea sparks something useful.

The project is open source. You can see the overview at [alanworks.app](https://alanworks.app) or browse the code at [github.com/realmorrisliu/alan](https://github.com/realmorrisliu/alan).
