今年 2 月写[《Human in the End》](/thoughts/human-in-the-end-next-gen-agent-interaction-zh)的时候，我对 [Alan](https://alanworks.app) 的想法还很单纯：一个用 Rust 写的 Agent 运行时，借用图灵机的隐喻，让无状态的程序在有状态的纸带上跑起来。

具体是什么时候开始转向的，其实过去有点久，我已经记不太清了。只记得后来有段时间，我在 Alan 上并行推进了很多东西——各种插件、各种 App、各种不同的 UI 形态。做着做着，心里越来越别扭，总觉得底层的抽象不太对劲。每加一种形态，上面就要多一层适配，各个模块之间越缠越乱。

我一直很喜欢 Unix。既然之前已经用图灵机来理解 Agent 了，我当时就冒出一个念头：为什么不能真的做一个类似 Unix 的东西？Agent 时代的 Unix 会长什么样？Agent 到底该怎么真正融进操作系统里，而不是一直作为外挂飘在应用层上面？

带着这几个问题翻了不少资料，最后看到了 **Plan 9**。越看越觉得它跟我脑子里的东西对上了。Alan 底层的系统层后来就叫 **`alan9`**，算是从这里开始的。

## 把 Agent 当成文件系统

Plan 9 最核心的想法大家都很熟：**everything is a file**。

把它放到 AI 上，其实非常自然。往最底层看，大模型本质上就是一台生成字符的机器。既然输入输出本来就是字符流，为什么不能用一个文件、或者文件背后的 stream 来表示它？

顺着这个思路往下推，整个 Agent 都可以被看成一个文件系统（Agent as a filesystem）：模型是一条字符流，Agent 本身就是一个普通进程，它的状态、上下文、工具、记忆，都是挂载在它命名空间里的文件和目录。它能碰到什么，完全取决于命名空间里给它挂了什么。

对我来说，这不只是架构上好看，它背后还连着我对 AI 产品形态的一个判断：**对话式 UI 未必是 AI 时代的终极方案。**

聊天框很万能，但对大多数人和大多数场景来说，设计良好的垂直 UI/UX 依然非常有价值。我一直想做的是让各种不同的垂直 App 共享同一套 Agent 底座——比如我最近在折腾的 M3 和 [slowpage](https://github.com/realmorrisliu/slowpage)（一个面向阅读场景的 App）。坦白讲，它们的 UI/UX 离我理想中的状态还差得远，但沿着这条路做下来，我能感觉到思路本身是通的。

站在这些垂直 App 的视角来看，把 Agent 抽象成文件系统，最大的好处其实很朴素：你不用专门去处理 Agent 的输出。状态、事件和输出流在文件系统这一层就已经抽象好了，App 按读写文件的方式去对接就行，不需要和某套特定的对话协议或 SDK 死绑在一起。而且既然都是文件和文本流，平时在 Unix 里顺手的标准文本工具全都能直接拿来用。

不用每接一个新界面、或者加一个新能力，就重新发明一套 API。底座和上层 App 在文件系统这个边界上自然就接住了。

## 为什么放弃了 Alan for macOS

中间我其实还花过不少精力做 **Alan for macOS**——当时想自己做一个好用的终端管理器，从技术形态上看，跟最近挺火的 Superlogical 的 Rex 有不少相似的地方。

但真正在上面写代码的时候，我越来越明显地感觉到，很多事情混杂到一起了。窗口管理、终端交互和 Agent 底座本身的边界搅在一块，经常让人想不明白某个问题到底该归哪一层管。

后来停下来想了想我的最终目标，发现外面这个壳其实没那么重要，最起码在现阶段不是最重要的事。与其被一个终端壳分散注意力、反过来拖累对核心抽象的判断，不如干脆把它放掉，把精力收回到 Agent 底座本身，终端管理交给专门的终端工具就好。

现在回头看，把那一大块删掉之后，整个项目清爽了很多，思考问题也简单了不少。

## 关于显式边界，以及我现在的犹豫

在 `alan9` 的设计里，有一点跟现在市面上大多数 CLI Agent 反着来。像平时用习惯的工具，通常在某个目录里一敲命令，就会自动接管当前目录、顺手扫描本地配置、直接继承环境变量。而在 `alan9` 里，我一开始坚持的是很强的显式边界——目录必须显式挂载，包安装完也不会默认授予运行中的进程，不给隐式的全局访问。

当时这么做，主要是出于三方面的考虑。首先是安全，网上已经见过太多 Agent 误操作酿成灾难性后果的例子，默认把整台机器的上下文和权限敞开给它，心里始终不太踏实。其次是想借鉴一些容器化的理念，把边界从一开始划清楚，也是为了 Alan 以后能跑到更多环境里——哪怕是边缘计算这类场景——提前留好余地。最后是上下文工程，当时觉得只让 Agent 看到它真正需要看的东西非常重要。

不过说实话，这些主要是我当时的观察和思考，放到现在来看，里面有些判断可能已经不太对，或者有点过时了。边界收得太紧，日常用起来的摩擦就会变大，每次都要人去操心该挂什么、给什么权限，体验上并不自然。

这也是 Alan 接下来要认真想清楚的问题：**在守住基本安全边界的前提下，怎样让 Agent 更智能地拿到它真正需要的东西**，而不是一刀切地把门全锁死。

## 一点期待

Alan 到今天依然处在很早期的阶段。不管是底层的 `alan9`，还是上面跑的几个垂直 App，都还有很多没打磨好的地方，甚至前面提到的很多判断，过半年我可能又会推翻重来。

把这些写出来，也不是想宣布什么已经完工的方案。只是觉得 **Agent as a filesystem** 是个挺优雅的抽象——把 AI 放回文件、流和命名空间这些老派但经得起时间考验的原语里，很多原本缠在一起的问题会突然变得清楚。如果你也在琢磨 Agent 的架构或者交互形态，希望这个视角能给你带来一点灵感。

项目本身都在开源推进，概览在 [alanworks.app](https://alanworks.app)，代码放在 [github.com/realmorrisliu/alan](https://github.com/realmorrisliu/alan)。
